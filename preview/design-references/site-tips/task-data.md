# 共享任务数据源

## 安装位置

- `task-registry.js` → `preview/src/mock/task-registry.js`
- `use-network-tasks.js` → `preview/src/hooks/use-network-tasks.js`
- `context.jsx` → `preview/src/context.jsx`

`AppProvider` 暴露 `networkTasks` 与 `openNetworkTask(id)`。首页指标、关注事件、地图站点 tips 应只读取 `networkTasks`，不再启动自己的计数器。

## 数据口径

- `tasks` 是唯一任务记录集合。`revision` 表示任务集合更新。
- `metrics` 为全部任务汇总，`centers[id].counts` 是相同记录按数据中心过滤后的汇总。
- `events` 默认呈现20条任务事件，人工待接管置顶，其次处置中，再补最近已完成记录；已完成事件的 `status="completed"`，不会伪装为处置中。若真实开放任务超过20条，全部呈现，优先保证真实状态。
- `status`：`analyzing`、`running`、`paused`、`awaiting-review`、`completed`、`cancelled`。
- `title` 是业务任务名；`scope` 是任务范围；`phase` 是当前步骤；`result` 内才放设备数、规则数等结果指标。
- 全网 UC1 任务 `centerId=null`，因此各数据中心的任务数之和可比全量任务数少全网任务数。
- UC4 HCS1 显式映射西三旗，依据原稿站点实例“西三旗数据中心 HCS”的文案。报告中的 HCS1 设备及规则数据未改变。
- UC3 属于首页 generation 技能统计，但名称明确为“生成检查规则”，并不冒充设备配置生成。

## 数据中心资源与检查范围

`networkCenterInventory` 是共享资源清单。西三旗的核心、接入、防火墙数量直接汇总 `devices.sourceGroups`，分别为160、140、80，总计380台网络设备；地图中的 Spine/Leaf 标签在本原型分别映射核心/接入组，仅用于资源展示。服务器320台单独保留，不属于这次HCS1网络配置检查范围。嘉定网络设备8+64+4=76台、服务器256台；外高桥网络设备12+72+6=90台、服务器288台。

`centerNetworkDeviceCount(id)` 仅汇总核心/接入/防火墙。资源数、检查样本数、任务数是不同维度，不能相加。静态告警数量也不等同于合规失败设备数。

历史 demo 的 UC4 完成/待审阅结果按所属中心的网络清单计算设备数，并重算通过数使其等于总数减失败设备数；UC2历史demo样本数不得超过该中心网络库存。实际UC2西三旗样本仍为100台，实际UC4 HCS1仍为西三旗380台；其他中心UC4任务只能查看摘要，不能套用HCS1画布执行。

初始记录309条：配置检查12（待验证1、分析中3、已完成8）、生成294（处理中1、完成293）、故障3（进行中1、完成2）。`generatedTotal` 从记录数派生为309，资源数不混入任务数。初始事件20条，其中待接管1、处置中5、已完成历史14；5条处置任务均有数据中心归属，UC1全网查询初始是已完成历史。

`centers[id].runningTasks` 与事件列表 `processing` 使用相同记录集合（本站运行、分析、暂停任务）。任务若实际暂停，仍保留 `status="paused"`，地图应呈现暂停状态，不能播放执行动效。`counts.processing` 与该数组长度一致；`counts.running` 只统计真正运行/分析中的记录，`counts.paused` 另列。全网UC1运行时不虚构地图站点。

## 实时与流程状态

Provider 中仅一个后台计时器迁移 `source=demo` 的记录；浏览器隐藏时暂停演示更新。UC1–UC4 开始时建立或接管 `source=workflow` 的任务，阶段、完成和暂停由现有 context 状态观察更新，演示计时器不会覆盖 workflow。站点默认 tips 优先当前真实 workflow，再取运行、待审阅、暂停或最近完成任务。

演示时钟间隔为8–12秒，首次变化也至少等待8秒。每次仅推进一条demo进度，完成或补入少量任务；新任务优先分配至处置中任务最少的站点，初始为西三旗2、嘉定2、外高桥1。纯 `phase / progress` 更新保留 `updatedAt`，不会让卡片反复重排；真实状态变化与新任务才更新关注排序时间。实际 UC1–UC4 文本、画布和完成回调仍使用既有节奏，不受演示间隔影响。

演示时钟将全局处置中数量尽量维持4–6，人工待接管维持1；只完成/推进demo记录，并创建真实的新demo任务补位。真实workflow有待审阅项时，demo审阅项可被模拟处置，不覆盖真实审阅状态。若真实workflow本身超过数量目标，真实状态优先，不隐瞒任务或伪造完成。

UC4 执行完成后进入 `awaiting-review`（原稿“任务完成，待审阅”），不合规设备数仍放在结果中；执行成功与人工审阅分开。仅真实停止/暂停才标记 `paused`：UC2 离开会停止其计时器，欢迎页会停止当前流程；单纯回首页隐藏 UC1/3/4 不主动暂停，后台实际阶段仍回写账本。

## 打开任务的边界

- 当前会话 UC2 画布与 UC4 已生成报告可直接恢复，不重启已完成任务。
- UC1/UC3 的当前挂载会话可重新显示；聊天已被欢迎页替换后，其局部时间线无法安全恢复，显示历史摘要提示，不伪造结果。
- 历史 demo 完成/待审阅记录只有摘要，不冒充完整报告。
- 可执行的未完成 demo 记录可被该 UC 接管，先变为真实执行态；接管时保留原记录的 `centerId / scope / title`，不会暗中换站点。实际 UC4 HCS1 仅支持西三旗，其他中心的 UC4 记录只读摘要；全新 UC4 入口默认对应西三旗 HCS1。
- 故障治理没有对应四个 UC 的详情时仅提示摘要，不伪造故障处置流程。
